# Spec — Internacionalização (i18n)

> **Status: planejado — ainda não implementado.** Esta é a especificação da feature
> de internacionalização. Faz parte das **features a implementar** (ver também
> [roadmap.md](../roadmap.md)).

## Objetivo

Suportar três idiomas na interface (web + mobile):

| Código | Idioma | Locale base |
|---|---|---|
| `pt` | Português | `pt-BR` |
| `en` | Inglês | `en-US` |
| `es` | Espanhol | `es-ES` |

- Idioma **padrão / fallback: `en`**.
- O idioma escolhido pelo usuário é **persistido no banco** (preferência por-usuário) e
  sincroniza entre dispositivos.
- A tela de **login/registro** (antes de autenticar) segue o **idioma do sistema** do
  dispositivo — ainda não há preferência do usuário para aplicar.

## Motivação

Hoje as strings de UI estão majoritariamente em inglês, com textos em português soltos
(overlay "Em breve" do dashboard, card de teste de notificação em settings, checkbox
"Dias com horários diferentes" no form de hábito). Esta feature elimina essa
**inconsistência de idioma** movendo todo texto visível para arquivos de tradução.

## Fonte de verdade e resolução do idioma

A **fonte de verdade** é o campo `User.Language` no banco. O cliente mantém um **cache
local** apenas para escolher o idioma instantaneamente no boot (antes de a API
responder) e funcionar offline.

**Ordem de resolução do idioma ativo:**

| Momento | Idioma usado |
|---|---|
| App abre, **antes do login** (login/registro) | Idioma do **sistema** (`expo-localization`) → se não suportado, `en` |
| **Registro** de novo usuário | Cliente envia o idioma detectado do sistema → vira o `User.Language` inicial |
| App abre **autenticado** / logo após login | `User.Language` (vindo do perfil) → aplicado e gravado no cache local |
| Boot offline (autenticado) | Cache local (último `User.Language` conhecido) → revalida quando a API responder |
| Usuário troca em **Configurações** | Atualiza imediatamente a UI + cache local + envia ao backend (`PUT /users/me/language`) |

> Em resumo: **sistema** governa o pré-login; **banco** governa o pós-login; o **cache
> local** só serve de atalho de boot, nunca como fonte de verdade.

## Backend (espelha exatamente o `Timezone`)

`Language` é uma preferência por-usuário idêntica em forma ao `Timezone`, que já existe
e está em produção. Mudanças necessárias:

1. **Domain — `User`** (`Domain/Entities/User.cs`)
   - Novo campo `public string Language { get; private set; }`.
   - Método `UpdateLanguage(string language)` com validação.
   - Validação `ValidateLanguage`: aceitar apenas `pt`/`en`/`es` (lançar `DomainException` caso contrário). Definir um conjunto suportado único e reutilizável.
   - Construtor passa a receber `language` (com valor inicial); manter `en` como default seguro se vazio.
2. **Application**
   - `UpdateLanguageCommand(Guid UserId, string Language) : IRequest` (em `Users/Commands`).
   - `UpdateLanguageHandler` — carrega o usuário, chama `user.UpdateLanguage(...)`, persiste.
   - `UpdateLanguageCommandValidator` — `UserId` não vazio; `Language` ∈ {pt,en,es}.
   - `UserProfileResult` ganha `string Language` (em `Users/Queries`).
   - `RegisterCommand` ganha `Language` (o cliente envia o idioma do sistema no registro); `RegisterCommandValidator` valida o conjunto suportado.
3. **Api — `UsersController`**
   - `PUT /users/me/language` → `UpdateLanguageCommand` (mesmo formato de `PUT /users/me/timezone`).
   - `UpdateLanguageRequest(string Language)`.
4. **Infrastructure**
   - Configuração EF do novo campo (provavelmente `required`, length curto) + **migration** nova (`AddUserLanguage`).
   - Migration deve definir default `'en'` para linhas existentes (back-fill).
5. **Contrato** — após as mudanças de DTO/endpoint, **regenerar o api-client**
   (`npm run api:generate`, com a API no ar). Surgem `usersUpdateLanguage`,
   `Language` em `UserProfileResult` e no `RegisterRequest`.
6. **Testes (TDD)** — unitário de `User.UpdateLanguage` (aceita suportados, rejeita
   inválido), do `UpdateLanguageHandler` e do validator; integração do
   `PUT /users/me/language` (200/204, 400 inválido, 401 sem auth, 403/isolamento).

## Frontend

### Stack
- **`i18next` + `react-i18next`** — interpolação, plural, namespaces, troca em runtime.
- **`expo-localization`** — detecta o locale do dispositivo (pré-login e no registro).
- **`language-storage`** — cache local do idioma, no mesmo padrão de
  `src/auth/token-storage.ts` (SecureStore mobile / AsyncStorage web).

### Estrutura de arquivos (padrão feature-based)

```
src/
  i18n/
    index.ts            ← init do i18next (cache → sistema → fallback en)
    locales/
      en.json
      pt.json
      es.json
  settings/
    queries.ts          ← + useUpdateLanguageMutation (PUT /users/me/language)
```

- Chaves por feature/tela: `common.*`, `auth.*`, `timeline.*`, `habits.*`,
  `dashboard.*`, `settings.*`, `validation.*`.
- Sem strings hard-coded — todo texto visível passa por `t("chave")`.

### Integração com o que já existe
- **`auth-context.tsx`** — após login/refresh bem-sucedido, ao obter o perfil, aplicar
  `i18n.changeLanguage(user.language)` e gravar no cache local. No logout, voltar ao
  idioma do sistema.
- **Settings** — nova opção **"Idioma"** (PT/EN/ES). Ao escolher: `i18n.changeLanguage`
  na hora (UX instantânea) + `useUpdateLanguageMutation` para persistir no banco; em
  erro, reverter para o valor anterior e avisar.
- **Registro** — enviar o idioma do sistema no payload (junto do timezone já enviado).

## Requisitos funcionais

1. **Pré-login** (login/registro) usa o idioma do **sistema**; fallback `en`.
2. No **registro**, o cliente envia o idioma do sistema, que vira o `User.Language` inicial.
3. **Pós-login**, a UI usa `User.Language` (do banco), aplicado no boot e em cada login.
4. **Configurações → Idioma** permite trocar entre PT/EN/ES; a troca é **persistida no banco** e reflete imediatamente em toda a UI.
5. A preferência **sincroniza entre dispositivos** (porque mora no banco).
6. Cache local garante boot instantâneo e funcionamento offline; o banco é a fonte de verdade.
7. Todo texto visível vem de arquivo de tradução (nenhuma string hard-coded de UI).
8. Os três locales têm **paridade de chaves** (nenhuma chave faltando).
9. Datas/horas respeitam o locale (integrar com `src/date.ts`).
10. Mensagens de validação (Zod/RHF) também traduzidas (`validation.*`).

## Viabilidade técnica

**Sim, é viável e de baixo risco.** A persistência de idioma é estruturalmente
**idêntica** ao `Timezone`, que já existe e está coberto por testes:

| Peça | Já existe (Timezone) | A criar (Language) |
|---|---|---|
| Campo na entidade `User` | `Timezone` + `UpdateTimezone()` | `Language` + `UpdateLanguage()` |
| Command/Handler/Validator | `UpdateTimezoneCommand` … | `UpdateLanguageCommand` … |
| Endpoint | `PUT /users/me/timezone` | `PUT /users/me/language` |
| Campo no perfil | `UserProfileResult.Timezone` | `UserProfileResult.Language` |
| Exibição em Settings | timezone já mostrado | seletor de idioma |
| Cliente gerado (orval) | `usersUpdate... ` | regenerar após a mudança |

Pontos de atenção (não bloqueadores):
- **Migration com back-fill**: usuários existentes precisam de default (`'en'`).
- **Pré-login**: o login não pode depender do banco — por isso usa o idioma do sistema
  (sem chamada autenticada). Já contemplado na ordem de resolução.
- **Consistência do conjunto suportado**: definir `{pt,en,es}` num único lugar no
  backend (validação) e refletir no front (locales) — evitar divergência.
- **Datas/números**: garantir que os helpers de `src/date.ts` recebam o locale ativo.

## Critérios de aceite

- Antes de logar, a UI aparece no idioma do dispositivo (ou `en` se não suportado).
- Um novo usuário nasce com o idioma do sistema gravado no banco.
- Trocar o idioma em Configurações persiste no banco, reflete na hora e **sobrevive a
  reinstalar o app / logar em outro dispositivo**.
- `grep` por strings de UI hard-coded nas telas não retorna texto visível.
- Os três locales têm paridade de chaves.
- Testes (unit + integração) do fluxo de `Language` no backend passam.
